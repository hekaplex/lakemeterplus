# Feature Comparison — `databricks-cost-observability` vs `lakemeter-oss`

## One-line framing

**`databricks-cost-observability`** answers *"what am I actually spending, right now, and is anything wrong?"* (retrospective/live observability over real Unity Catalog billing + platform telemetry).
**`lakemeter-oss`** answers *"what would this workload cost if I built it?"* (prospective/hypothetical cost estimation and proposal generation).

They are largely **complementary rather than duplicative** — the main overlap is DBU/cost-domain knowledge (SKUs, pricing, product types) and Databricks-Apps-style header-based auth. This is the key finding shaping the merge plan.

## Side-by-side comparison

| Dimension | `databricks-cost-observability` | `lakemeter-oss` |
|---|---|---|
| **Primary purpose** | Live cost & governance **observability** dashboard over actual historical spend | Pre-purchase **cost estimation** / sizing calculator for hypothetical workloads |
| **Backend framework** | FastAPI, `pyproject.toml` v1.0.0 | FastAPI, backend `app/main.py`, v1.0.0 |
| **Frontend** | Single hand-authored `static/index.html` (8.2K lines), vanilla JS, Chart.js + D3 + 3d-force-graph, **no build step, no framework** | React 18 + TypeScript 5.3 + Vite 5 + Tailwind, Zustand state, React Router, `@dnd-kit`, `framer-motion` — modern component SPA |
| **Data access layer** | **No app-owned DB for core features.** Reads Unity Catalog `system.*` tables live via Databricks SDK Statement Execution API (SQL Warehouse REST calls). No ORM, no SQLAlchemy | **Owns Lakebase (managed Postgres)** via SQLAlchemy ORM for app data (users/estimates/line items) + `sync_*` reference tables fed from UC by a separate ETL |
| **Cost-calculation logic** | N/A (reports actual billed cost, doesn't calculate hypothetical cost) | PL/pgSQL functions in Postgres (`calculate_line_item_costs` orchestrator + per-workload DBU/VM calculators) |
| **Own persisted tables** | `app_user_permissions` (per-user tab access), `platform.cloud_platform_costs` (multi-cloud billing, notebook-fed) | Full app schema: `users`, `estimates`, `line_items`, `templates`, `sharing`, `conversation_messages`, `decision_records`, plus `sync_*` pricing tables |
| **Demo/offline mode** | `MOCK_MODE` — regex-rewrites `system.*` → `workspace.mock_system_*` so it runs on any workspace tier without real system-table access | Client-side pricing bundle (`static/pricing` CSVs) enables instant local calculation without a round-trip; no equivalent "mock system tables" concept since it doesn't depend on `system.*` for core function |
| **AI feature** | **None** — the "AI" tab is analytics *about* AI Gateway/model-serving usage & cost (observability of AI spend), not a chatbot. Uses SQL `AI_FORECAST()` for spend projection and `IsolationForest` (scikit-learn) for anomaly detection | **Full AI Assistant** — Claude via Databricks model-serving endpoint, tool-calling (`propose_workload`, `analyze_estimate`, etc.), SSE streaming chat, natural-language → workload-config proposals |
| **Auth model** | Databricks Apps forwarded headers (`X-Forwarded-User` etc.) + `ALLOWED_USERS`/`ADMIN_USERS` env-var allowlists; per-user tab/workspace restriction system backed by a Delta table | Databricks Apps forwarded headers (`X-Forwarded-Email` etc.) + Service-Principal OAuth used *both* for user identity *and* to mint short-lived Lakebase DB credentials |
| **Domains covered** | 17 observability domains: Executive, Cost, ML Anomalies, User Adoption, Compute Sizing, Query Attribution, AI/LLM usage, UC Access Graph, Job SLA (Lakeflow), Storage, Lineage & ML, Governance, Cluster Health, Marketplace, Platform Ops, Cloud Cost (multi-cloud), Alerts | 12 workload-type cost calculators: Jobs, All-Purpose, DBSQL, DLT/SDP, Model Serving, Vector Search, FMAPI (Databricks + Proprietary), Lakebase, Databricks Apps, AI Parse, Shutterstock ImageAI, Lakeflow Connect |
| **Alerting** | Rule-based spend-spike detection (`AlertService` + a duplicated standalone `scripts/send_cost_alerts.py` for scheduled-job use), SMTP email, admin-configurable threshold | None — estimates are static/exportable, not monitored over time |
| **Export** | None (dashboard-only, no report export) | Excel export (`xlsxwriter`) with SKU/discount/VM pricing detail, per-workload formatting |
| **Multi-cloud scope** | Databricks DBU cost (via UC) **and** separate multi-cloud infra cost (Azure Cost Management/AWS Cost Explorer/GCP Cloud Billing) via `cloud_cost.py` | Multi-cloud **pricing inputs** (AWS/Azure/GCP VM instance pricing) for estimation, not multi-cloud spend monitoring |
| **Security hardening** | Heavy: CSP, HSTS, tiered sliding-window rate limiting, bot/scanner UA detection, progressive IP banning, structured audit logging, strict regex input validators for SQL-identifier interpolation (no parameterized DDL API available) | Standard: CORS restricted to same-origin in prod, Pydantic-validated inputs, SQLAlchemy parameterized queries (lower injection surface since it's a real DB driver, not string-interpolated SQL) |
| **Testing strategy** | Minimal — one `tests/smoke_test.py` (413 lines), live black-box HTTP smoke test only, no unit tests, no pytest suite | Extensive — pytest suite covering `harness` (ordered user-journey), `parity` (frontend/backend calc cross-check), `export`, `regression`, `ai_assistant` (live-endpoint, opt-in), `test_integration_validation`, `schema` |
| **CI/CD** | `deploy.yml` (deploy on push to main) + manual `load-enterprise-data.yml`; **no test/lint CI step** | `ci.yml` — Python compile + stable pytest subset + frontend `npm run build` on every PR/push |
| **Deployment mechanism** | Databricks Asset Bundle (`databricks.yml`), single `apps` resource, 2 targets (dev/prod), deployed via GitHub Actions | Databricks Asset Bundle (`scripts/databricks.yml`), 9-task job DAG (provision Lakebase → create DB/functions → load pricing → create app → grant access → deploy → verify), one-command `scripts/install.sh` |
| **Deployment maturity signal** | Hardcoded warehouse ID (`21f5bd20b7f44a51`) left in `app.yaml`/workflow; `deploy.yml` prod path references `dev` bundle files (latent bug) | Two parallel/overlapping installer implementations found (`scripts/install_lakemeter.py` legacy script vs. DABs notebook pipeline) — needs reconciliation even within its own repo |
| **License** | Elastic License 2.0 (no hosted/managed-service redistribution to third parties) | Databricks License (use tied to Databricks Services agreement) — **different license terms; must be reconciled before merging code** |
| **Maturity / release history** | v1.0.0, has a `ROADMAP.md` with in-progress/planned/completed sections; single maintainer style (personal GitHub org) | v0.1.0, single changelog entry ("Initial public open-source release", 2026-07-24) — official Databricks Labs OSS project |
| **Shared/overlapping concepts** | DBU/SKU pricing knowledge, `system.billing.list_prices`, product-type/SKU-name mapping, Databricks-Apps forwarded-header auth pattern, admin-vs-user access distinction, env-driven config via Pydantic Settings | Same DBU/SKU pricing knowledge (independently sourced via its own `pricing_sync` ETL rather than live `system.billing` queries), same auth header pattern, same Pydantic Settings config style |

## Implication for merge strategy

Because the overlap is concentrated in **pricing/SKU domain knowledge and the auth pattern**, not in application logic, the lowest-risk merge treats the two as **two feature modules sharing one host app** (auth, config, deployment) rather than trying to unify their data-access layers (Statement-Execution-over-UC vs. SQLAlchemy-over-Lakebase are architecturally incompatible to merge into one abstraction without a rewrite). See `merge-tasks.md` for the concrete task breakdown.
